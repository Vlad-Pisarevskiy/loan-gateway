# Loan Gateway

Сервис-шлюз маркетплейса финансовых продуктов: принимает заявку на кредит наличными, рассылает её в банки-партнёры через адаптеры и собирает их решения.

## Как это работает

- `gateway api` принимает заявку (`POST /v1/applications` с заголовком `Idempotency-Key`) и в одной транзакции создаёт по задаче «отправить в банк» на каждый банк.
- `gateway worker` забирает задачи через `FOR UPDATE SKIP LOCKED`, вызывает адаптеры банков, ретраит временные ошибки с backoff и возвращает в очередь задачи упавших воркеров.
- Асинхронный банк присылает решение вебхуком с HMAC-подписью.
- Клиент опрашивает `GET /v1/applications/{id}`, пока заявка не станет `completed`.
- Метрики Prometheus и трейсы OpenTelemetry показывают состояние шлюза и путь каждой заявки через очередь.

В MVP банки эмулируются заглушкой `mockbank`; у каждого свой протокол:

| Банк | Протокол | Поведение в docker compose |
|---|---|---|
| northbank | синхронный JSON, рубли строкой | отвечает сразу |
| eastbank | синхронный JSON, копейки | отвечает за 1 с; по каждой заявке первые 2 попытки — 503 |
| westbank | асинхронный: 202, решение вебхуком | вебхук через 5 с |

## Быстрый старт

Нужны Docker с compose, `curl` и `jq`.

```bash
make up     # PostgreSQL, миграции, API, воркер и три банка
make demo   # отправить заявку и дождаться решений
make down
```

## Наблюдаемость

`make up` поднимает и стек наблюдаемости, `make demo` в конце печатает ссылки на дашборд и трейс заявки.

| Что | Где |
|---|---|
| Дашборд Grafana «Loan Gateway»: нагрузка API, задержка и исходы по банкам, очередь, вебхуки | http://localhost:3000/d/loan-gateway |
| Prometheus: метрики и алерты (`TargetDown`, `BankErrorRateHigh`, `QueueBacklog`, `CallbackTimeouts`) | http://localhost:9090/alerts |
| Jaeger: трейс заявки — API, все попытки по каждому банку и вебхук westbank в одном трейсе | http://localhost:16686 |

Метрики `api` и `worker` — на `:9100/metrics` внутри сети compose (на хост порт не проброшен; снаружи метрики видны через Prometheus). В логах записи о запросах и задачах содержат `trace_id`. Подробно — раздел 14 [спецификации](docs/spec.md).

## Как разрабатывался проект

Проект сделан агентами Claude Code по процессу «спецификация → план → реализация»:

1. Спецификация и план написаны в диалоге с агентом: требования, варианты архитектуры, дизайн по частям, затем пошаговый план с кодом и тестами.
2. Каждая задача плана — отдельная ветка и PR в `develop` (gitflow). Роль `developer` реализует задачу через TDD, роль `reviewer` проверяет её по спеке и чек-листу — см. `.claude/agents/`. Задачи 7–10 основная сессия реализовала и проверила сама, без отдельных ролей; затем они вместе с Task 13 прошли независимое ревью (PR #19).
3. Фундамент (Task 1–10 и 12) делался локально и последовательно; northbank, сборка, e2e, compose и адаптеры eastbank и westbank (Task 11, 13–17) — в облачных сессиях, параллельно там, где позволяли зависимости.
4. Каждый PR проходит CI: gofmt, go vet, golangci-lint и все тесты с `-race`.
5. v0.2.0 (наблюдаемость) — тем же процессом: раздел 14 спеки, план `docs/plan-observability.md`, 7 задач; основа и сборка локально, HTTP API, воркер и инфраструктура — в трёх параллельных облачных сессиях.

Итоги по [журналу разработки](docs/dev-log.md): задач в планах — 25 (v0.1.0 — 18, v0.2.0 — 7), PR из feature-веток — 28, замечаний ревью исправлено — 23 из 132, облачные сессии — $18 (v0.1.0 — $11, v0.2.0 — $7).
